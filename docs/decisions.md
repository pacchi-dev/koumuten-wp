# 決定事項と理由

「なぜその選択をしたか」「なぜ他の選択肢を採らなかったか」を残す。
実装の詳細は `design.md`、プロジェクトの前提は `../CLAUDE.md`。

---

## D-01 オリジナルテーマで作る

**決定**: 既製テーマ（SWELL / Lightning / Elementor 等）を使わない。

**理由**: 工務店・建設会社の WordPress サイト 50 件を解析した結果、
オリジナルテーマが 76%、既製テーマは **0 件**だった。オリジナルテーマが業界標準であり、
「なぜ既製テーマを使わなかったか」を README で弁明する必要はない。

---

## D-02 フォームは Contact Form 7

**決定**: CF7 を入れる。自作しない。

**理由**: 解析した 50 件のうち CF7 が 42%（CF7 系プラグイン込みで過半数）で最多だった。
発注者が「CF7 で作ってほしい」と指定してくる可能性が高く、
既存案件の改修を引き継げることを示す価値がある。

**既存ポートフォリオとの関係**: `portfolio_wordpress` ではフォームを自作した。
両方扱えることを README で説明する。

| | 長所 |
|---|---|
| CF7 | 発注者が管理画面から項目を変更できる |
| 自作 | 依存が減り軽い。バリデーションを完全に制御できる |

---

## D-03 ACF は無料版。Repeater と Options Page を使わない

**決定**: ACF 無料版で完結させる。

**理由**: ACF Pro は有料（年間ライセンス）。発注者に追加コストを負わせない構成を
選べることを示したい。CrowdWorks の実案件に
「保守・運用の費用が掛からないようなホームページ作成を希望します」という記載があった。

**回避策**:

| Pro 機能 | 代替 |
|---|---|
| Repeater（可変長の繰り返し） | textarea に 1 行 1 レコード（`項目,値`）を入力し、テーマ側でパース |
| Repeater（件数が固定） | `group` フィールドに固定個のサブフィールド（例 Instagram の6枚） |
| Options Page（サイト共通設定） | **カスタマイザー**（D-04） |

**トレードオフ**: textarea 方式は入力フォーマットのミスに弱い。
そのためフィールドの `instructions` に記入例を必ず書き、
テーマ側のパーサは不正な行を握りつぶして落ちないようにする。

---

## D-04 サイト共通設定はカスタマイザー、置き場所はプラグイン

**決定**: 電話番号・住所・営業時間などをカスタマイザーに置く。
登録はテーマではなく**プラグイン**から行う。

**理由（カスタマイザーにする）**: ACF 無料版に Options Page が無い。
固定ページに共通設定を紐付ける回避策もあるが、
「会社の電話番号がトップページの編集画面にある」のは運営者にとって不自然。
カスタマイザーはライブプレビューがあり、非エンジニアの発注者に説明しやすい。

**理由（プラグインに置く）**: 会社情報はテーマを差し替えても残るべきデータ。
カスタマイザー API はプラグインからも使えるため、責務の分離を優先した。

**将来**: ACF Pro を導入するなら `acf_add_options_page()` に統合できる。

---

## D-05 Web フォントを読み込まない

**決定**: Google Fonts 等を使わず、OS 標準の日本語ゴシックを使う。

**理由**: 日本語 Web フォントはサブセットでも数百 KB になる。
本サイトはトップの `<img>` が業界中央値で 55 枚という「写真が主役」の構成であり、
帯域は写真に使うべき。**画像最適化を最重要要件に置いた以上、
フォントで数百 KB を消費するのは方針と矛盾する。**

**トレードオフ**: 環境によって見え方が変わる。
そのため字送り・行間をトークンで統一し、フォント差が出にくい設計にする。

---

## D-06 Instagram は API を使わない

**決定**: ACF 管理の 6 枚グリッド + 公式アカウントへの外部リンクで実装する。

**理由**:

1. Instagram Basic Display API は **2024 年 12 月に廃止**された
2. oEmbed は Meta のアプリ審査（`oembed_read`）が必要で、審査に通らないと表示できない
3. そもそも本サイトは架空企業であり、実アカウントが存在しない

**実装**: 画像は施工実績の写真を流用する（素材の追加ダウンロードは不要）。
実アカウント運用時の差し替え手順を README に書く。

---

## D-07 ローカルに Mailpit を同梱する

**決定**: `docker compose` に Mailpit を追加し、mu-plugin で SMTP を向ける。

**理由**: 素の WordPress コンテナには MTA が無く `mail()` が外に出ない。
CF7 は「送信しました」と表示するが実際にはメールが生成されないため、
**「フォームが送信できる」を検証できない**。完了条件を検証可能にするために必要。

**本番への影響**: 差し替えは `wp_get_environment_type() === 'local'` のときだけ行う。
レンタルサーバーへ移設してもファイルを消す必要がなく、標準の `mail()` に戻る。
WP Mail SMTP 等のプラグインは入れない（プラグイン最小限の方針）。

---

## D-08 ヒーローのコントラストはスクリム α で理論保証する

**決定**: 文字が乗る領域の黒スクリムを **α 0.54 以上**にする。

**理由**: 写真背景は画素ごとに輝度が違うため、
「たまたま今の写真で 4.5:1 を満たした」では写真差し替えで壊れる。

WCAG の相対輝度から逆算すると、黒 α ≧ 0.535 のとき、
背景が純白（相対輝度 1.0）でも白文字とのコントラストが 4.5:1 を上回る。

| α | 合成後の輝度値 | コントラスト比 |
|---|---|---|
| 0.50 | 0.500 | 3.98 ✗ |
| 0.535 | 0.465 | 4.51 ✓ |
| 0.54 | 0.460 | 4.59 ✓ |

**検証**: 理論保証に加えて、合成後のスクリーンショットから
文字のバウンディングボックス内を格子状に 20 点以上サンプリングし、
**最も明るい画素**（白文字にとっての最悪値）で実測する。

## D-09 施工実績の詳細は「松尾工務店型」

**決定**: メイン写真 1〜2 枚 + 間取り図 + 物件概要テーブル + 本文。

**理由**: 実サイトの詳細ページは画像枚数に大きな幅があった
（ネイエ設計 230 枚 / ボックス・ワン 15 枚 / 松尾工務店 6 枚）。
フリー素材では「同一物件の別カット」を複数枚揃えることが困難で、
無理に枚数を増やすと**別々の家の写真が並んで破綻する**。

松尾工務店型は物件概要テーブルが情報の主役になっており、
素材制約と情報設計の両方に適合する。

---

## D-10 間取り図はインライン SVG を自作する

**決定**: ラスタ画像を使わず、ACF のテキストデータから SVG を生成する。

**理由**: リクエストを増やさない / `currentColor` でテーマに追従 / 拡大しても劣化しない。
加えて、フリー素材に「その物件の間取り図」は存在しないため、自作する以外の選択肢が無い。

**データ駆動にした理由**: SVG をテンプレートに直書きすると物件ごとに
テーマファイルを編集することになり、「運営者が自分で更新できる」という方針に反する。

---

## D-11 お知らせは通常投稿を使う

**決定**: CPT を作らず、標準の投稿（post）を `/news/` に割り当てる。

**理由**: カテゴリ・アーカイブ・RSS・検索が標準機能のまま動く。
CPT を増やすと同等の機能を自前で用意することになり、保守コストが上がる。

---

## D-12 架空であることの明示（4 項目・必須）

ストックフォトを施工実績として掲載するため、実在の施工写真だと誤認されない手当てを入れる。

1. README に「架空の企業を想定した制作物」であることを明記
2. フッターに「本サイトは架空の企業を想定した制作サンプルです」を 1 行
3. 施工実績（一覧・詳細）にサンプルである旨の表記
4. 写真素材の出典一覧（配信元 URL）を README に記載

**この 4 項目はハードコードする。** ACF やカスタマイザーで編集可能にすると
運営者が消せてしまい、明示の意味が無くなるため。
「ハードコードした箇所は README に理由とともに記載する」という方針に従い、README にも書く。

社名・住所・電話番号もすべてダミー（郵便番号 `670-0000`、番地 `0-0-0`、
電話 `079-000-0000` はいずれも実在しない形式）。

### 出典一覧に撮影者名を載せていない理由

当初の想定では「URL・撮影者名」を載せるつもりだったが、撮影者名は省いた。

1. **ライセンス上、不要**。Pexels / Unsplash はいずれもクレジット表記を必須としていない
   （Unsplash は任意の慣習として推奨しているが、要件ではない）
2. **この一覧の目的を配信元 URL で満たせる**。目的は「掲載写真がストックフォトであり、
   実在の施工写真ではない」と示すことで、URL があれば写真を一意に特定できる。
   撮影者名はこの目的に寄与しない
3. **取得コストと保守が見合わない**。撮影者名の取得には各サービスの API キーが必要で
   （検索ページ・写真ページはボット保護のため到達できない）、キーの管理と失効対応が増える

将来 API キーを用意して撮影者名を追記することは可能。その場合も
`bin/fetch-images.sh` の URL 一覧が対応表になる。
